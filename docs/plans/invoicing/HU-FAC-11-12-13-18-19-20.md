# HU-FAC-11, 12, 13, 18, 19, 20 · Credit notes, SIAT system status and VAT books — plan

> Approved 16 Nov 2026. Build with `/story-build HU-FAC-11 HU-FAC-12 HU-FAC-13 HU-FAC-18 HU-FAC-19 HU-FAC-20`.

## Context

HU-FAC-01…10 (branch `feat/hu-fac-01-10`) built invoice issuing against a `SiatGateway` port with a simulator. An approved return already writes a `CreditNote` row in `PENDING`, but nothing issues or shows it; there is no screen for CUIS/CUFD health, and no VAT books. These six stories add them.

- **HU-FAC-14…17 are RETIRED** (contingency, client rule of 12 Nov) and are not planned.
- **Story source:** the Sheet "Rodalaser Product Backlog v2" (`docs/backlog/invoicing.md` only holds 01–10; the build adds these six rows there).
- **Decided in planning (16 Nov):**
  1. HU-FAC-19 gets its own table `purchase_book_entries`, seeded with demo data; a later Compras story feeds it. No manual entry form.
  2. Credit notes are return-linked. Price-adjustment notes are built but sit behind `invoicing.allowPriceAdjustmentNotes = false`.
- **Branch:** `feat/hu-fac-11-13-18-20`, cut from `feat/hu-fac-01-10` (develop does not have the invoicing migration yet).
- **Figma** (`JYULL6jvXiwNP8UVvEF7tl`, page `136:8992`): FS-23, FS-24, FS-25, FS-05, FS-11, FS-08, FS-10, FS-38, FS-39. Node ids are not in the repo; read each frame with `get_design_context` before building its screen.

## Model

Migration **`20261116120000_invoicing_notes_books`** (after `20261113120000_invoicing_siat_issuing`; no other branch has unmerged migrations).

- **`CreditNote`** (exists) gains `branchId`, `pointOfSaleId`, `cuf`, `issuedAt`, `siatReceptionCode`, `rejectionCode Int?`, `rejectionMessage`, `lastAttemptAt`, `lastError`, `reasonCode Int`, `vatAdjusted Decimal(14,2)`; `returnId` becomes nullable (price-adjustment notes); `@@unique([companyId, pointOfSaleId, number])`. Back-fill existing rows from their invoice and return.
- **`CreditNoteItem`** (`credit_note_items`): `creditNoteId`, `saleItemId`, `description`, `quantity`, `unitPrice`, `amount`. CHECK `quantity >= 0`, `amount > 0`. Back-filled from `sale_return_items`.
- **`CreditNoteDocument`** (`credit_note_documents`, 1:1, `signedXml`), like `InvoiceDocument`.
- **`PurchaseBookEntry`** (`purchase_book_entries`): `period` (`YYYY-MM`), `date`, `supplierNit`, `supplierName`, `authorizationCode`, `invoiceNumber`, `total`, `vatCredit`, `status PurchaseBookStatus { VALID, OBSERVED }`, `observation`, `nitVerifiedAt`, `source`. `@@index([companyId, period])`.
- All four carry `company_id` and are registered in `TENANT_MODELS` (`apps/api/src/common/prisma/tenant.extension.ts`).
- `SiatPointOfSale` already has `cuis*`, `cufd*`, `lastSyncedAt`: no change.
- Number: `nextDocumentNumber` (`apps/api/src/modules/sales/document-sequence.ts`) with key `NC-<branch>-<pos>`, taken at the first send.

## Risks and doubts

1. **Purchases book has only seeded data** until Compras exists; its contract (`purchase_book_entries`) is what Compras must write.
2. **Draft period:** closing is HU-FAC-21 (not here). A period is a draft while its month has not ended; the closed flag arrives with HU-FAC-21.
3. **Simulator only:** nothing is certified against the SIN; note XML/PDF are "PROVISIONAL". Credit-note reason codes and the LCV column layout must be checked against the synced catalogue (HU-FAC-25) and the accountant.
4. **Back-fill** of existing `credit_notes` rows in the migration (reason, items, point of sale); rows whose invoice has no point of sale stay null and fail the first send with `POINT_OF_SALE_MISSING`, as invoices do.
5. **Size:** build in slices, each green before the next — (A) notes model, machine, issuing, 11/12 screens → (B) system status (13) → (C) sales book, purchases book, export (18–20).
6. **Sheet:** HU-FAC-14…17 still show "Diseñado"; not touched by the build.
